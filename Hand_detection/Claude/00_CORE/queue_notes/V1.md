> **STATUS** · ✅✅ **SHIPPED 2026-08-28** — default `facing_user`, orientation `pitch_yaw`
> **OWNS** · where the camera sits relative to the user's eyes, and every sign that follows from it

## 1. What the owner reported

> *"at the moment, the camera views the hands from the opposite side of the hands
> as the user does … when the hands rotate on yaw and pitch, the direction of the
> rotation shown on screen is opposite to what the user sees in the real world.
> Same for translation on the z axis."*

And the requirement that shaped the design, given the next day:

> *"remember that I need to be able to port my game to vision glasses, and in such
> case the camera view is aligned with the user view. Therefore I need to be able
> to toggle the flip: camera worn by user = current setup, camera facing user =
> this new setup"*

## 2. ⭐⭐⭐ THE DIAGNOSIS: THE SHIPPED BUILD IS A HYBRID OF TWO MOUNTINGS

> ✅✅ **CONFIRMED LIVE 2026-08-28** — `pitch_yaw`, the conjugation named below, is
> the one the owner accepted. ⚠ But read §6bis before trusting the reasoning: it
> was refuted on the first live look, survived only because a later A/B overturned
> that report, and the "predicted the symptom" framing was luckier than it looked.

The frame is mirrored **before** detection (`cv2.flip`, §14.3.4.3). After that
flip the landmark frame is:

* `x` in the **USER's** frame — the right hand appears on the screen's right;
* `z` still in the **CAMERA's** frame.

⛔ That mixed frame is a **REFLECTION** (determinant −1), which is not any
physical viewpoint at all. Completing it with a `z` negation gives
`diag(−1, 1, −1)` — a **proper rotation**, a 180° turn about the vertical, i.e.
literally the user's own viewpoint.

⭐ **The diagnosis PREDICTED the symptom rather than being fitted to it.**
Conjugating a rotation by `D = diag(1,1,−1)` gives `R(n,θ) → R((nₓ,n_y,−n_z), −θ)`:

| axis | under the change |
|---|---|
| yaw `(0,1,0)` | **REVERSED** |
| pitch `(1,0,0)` | **REVERSED** |
| roll `(0,0,1)` | **UNCHANGED** |

The owner named yaw and pitch and did **not** name roll. Nothing in the report
said roll was fine; the geometry said it, and the report agreed.

## 3. ⛔ THE SECOND MECHANISM, WHICH THE PROPOSED FIX COULD NOT REACH

Z-translation is **not** driven by landmark `z`. `palm_depth.py` says so in its own
header — *"NOT derived from `world_landmarks`"* — it is driven by the apparent
**pixel span**, through `cube.depth_m = grab_depth_m / ratio`.

Hand away from the user → toward the camera → span grows → `ratio > 1` → depth
shrinks → **the cube gets bigger as it is pushed away.** Inverted, exactly as
reported, and no change to the landmarks could have fixed it. It needed its own
sign, and it got one.

⭐ **A consistency check that fell out for free, and it is what confirms the whole
model**: `grab / ratio` is *correct for a head-worn camera*. Today's depth
handling was never wrong — it was only ever wrong for a **facing** camera. So the
shipped build takes its mirror from one mounting and its depth from the other.
That is the defect, stated in one sentence.

## 4. ⭐⭐ WHY THE LANDMARKS ARE NOT TOUCHED — AND THE PROOF THAT IT DOES NOT MATTER

The owner's proposal was to negate `z` on every landmark. That is **provably
equivalent** for everything on screen. Horn/Kabsch minimises `‖Ra − b‖`, and with
`a' = Da`, `b' = Db` (`D` orthogonal, `DD = I`):

    ‖R'Da − Db‖ = ‖D(DR'D)a − Db‖ = ‖(DR'D)a − b‖

so `R'_opt = D R_opt D` **exactly**, and `det(DRD) = det(R) = +1`, so it is still a
rotation. Every frame builder conjugates the same way (`F' = D F D` for a frame
built from cross products), and the grab-relative rotation conjugates too:
`R'_rel = (D R_now D)(D R_grab D)ᵀ = D R_rel D`.

⛔ **But negating the landmarks would also invert three things that must not
invert, and each is a scar this project already carries:**

1. **`signed_palm_volume`** — `U7`'s geometric chirality is a **determinant** over
   world `z`, so it changes sign. That is `U7`'s error class, which survived seven
   patches once and which `R1` committed again on 2026-08-27.
2. **`depth_order.landmark_depths` and `fingertips.grip_depth_m`** — `R1`'s
   occlusion. These are **metres from the camera** and must stay so: the hand
   pixels being composited come from the camera, so a finger the camera sees in
   front must be drawn in front, whatever the user's viewpoint is.
3. **All 37 golden-vector suites and all 415 recordings**, which are written in the
   camera's convention.

⭐ So the orientation is corrected by conjugating the quaternion **at the one point
both tools finalise it** — the line the code itself already marks as the parity
anchor (*"ONCE PER HAND, PER FRAME … Anything else and `parity_replay` diverges"*).
One line per tool reaches Horn, the raw fallback **and** `handinput`'s published
pose, and reaches nothing else.

⚠ **What this deliberately does NOT do**: it does not publish user-referenced
*landmarks*. `camera_mount.user_view_world()` exists and is tested for a future
consumer that wants them, but nothing calls it. Doing it at ingest instead is a
bounded follow-up needing exactly the three compensations above — it is not free,
which is why it is not the default.

## 5. What was built

**One setting, `Resources/camera_mount.py`, and everything derives from it** (`L1`:
a tuning constant lives in exactly one module). ⭐ It is in
`handinput/manifest.py`'s exported core, because the port to glasses is the entire
reason it exists — an input system that could not say which way the camera points
would push that decision onto every host that embeds it.

| mount | mirror frame | orientation | depth from ratio | chirality |
|---|---|---|---|---|
| `facing_user` | yes | `(w,−x,−y,z)` — `pitch_yaw`, ✅ owner-confirmed | `grab × ratio` | as today |
| `head_worn` | **NO** | unchanged | `grab / ratio` | as today |
| `legacy` | yes | unchanged | `grab / ratio` | as today |

> ⛔ **CORRECTED §6bis**: the chirality column originally read INVERTED for
> `head_worn`. That was wrong — the bit is mount-independent.

⛔ **RETRACTED IN §6bis — the paragraph below is WRONG and is kept as the record.**
It argued the chirality bit is a function of the MIRROR alone — `signed_palm_volume` is
a determinant, so a mirrored frame flips its sign and an unmirrored one does not.
`facing_user` and `legacy` therefore share today's value and only `head_worn`
inverts. That is why the orientation fix does not touch the landmarks: if it did,
this bit would turn over for `facing_user` too, taking `U7`'s whole subsystem —
slot naming, rule 3's gate, `U8`, DR-2 — with it, on a build whose only intended
change was a rotation **direction**.

⛔ `legacy` is **not a supported deployment.** It is the hybrid of §3, kept only so
`A10` and `parity_replay` can reproduce the pre-change baseline exactly and so the
owner can A/B. **It is the DEFAULT until the live look happens.**

Wired at 7 sites: the frame mirror (server ×2, debug ×1), the orientation (both
tools, at the parity anchor), the depth mapping (both tools), and the chirality
constant (derived, not hard-coded).

## 6bis. ⛔⛔ TWO RETRACTIONS FROM THE OWNER'S FIRST LIVE RUN (2026-08-28)

Both were found by **looking**, in two short sessions, after every offline check
had passed. Kept in full: the project's rule is that a claim overturned is worth
more than one silently deleted.

### ⛔ RETRACTION 1 — the chirality bit is NOT mount-dependent

Owner, on `head_worn`: *"the mentions left and right hands are inversed in the
user worn"*.

⭐ **The real defect was `hand_identity.anatomical_name`**, a hard-coded display
swap that exists ONLY to undo the mirror. With no mirror it stops correcting and
starts causing. Now derived from the mount; still display-only.

⛔ **But checking it exposed a second error, mine.** `chirality_v_negative_is_left`
had been made mount-dependent on the reasoning that `signed_palm_volume` is a
determinant and flips with the mirror. That half is true. The error was forgetting
that **the target flips too**: `geometric_chirality` replaces MediaPipe's label,
and MediaPipe calls an *unmirrored* right hand `'Right'`. Both flips cancel — the
bit is mount-independent and always `True`.

⛔⛔ **AND THE HARNESS HAD ALREADY SAID SO.** `verify_geometric_chirality` FAILED
under `head_worn` with `V<0 -> 'Left'` reading `'Right'` — reporting this exact
defect. It was misread as the fixture being bound to the mirrored convention and
**silenced with a mount guard**. The owner then found it by eye in one run.

⭐⭐ **THE METHOD RULE THIS EARNS, and it is `METHOD.md`'s own rule inverted.** The
standing warning is that a harness can report CLEAN on a build the owner watched
fail. This is the other direction: **a harness reporting a REAL defect and being
explained away.** *Suspecting the instrument is not the same as dismissing it.*
`analysis/mount_guard.py` now carries an explicit bar: a suite may be guarded only
once its claim has been re-derived independently and shown to be about a
convention rather than a defect. Both wrongly-added guards are removed.

### ✅ RESOLVED — `pitch_yaw` IS RIGHT, AND THE ROUTE THERE IS THE LESSON

Owner, on the first `facing_user` run: *"the yaw rotation of the cube is inversed
in camera facing"*. Taken at face value, that refuted `pitch_yaw`.

⭐⭐⭐ **THE CONSTRAINT THAT MADE THE SEARCH FINITE: a viewpoint change is a
CONJUGATION, and there are EXACTLY THREE.** For a diagonal `Q` it maps the
quaternion's vector part by `-Q_diag`, and reverses anything only when
`det(Q) = -1`. Each reverses **exactly two** axes:

| option | `Q` | quaternion | reverses | keeps |
|---|---|---|---|---|
| **`pitch_yaw`** | `diag(1,1,-1)` | `(w,-x,-y,z)` | **pitch + yaw** | **roll** |
| `yaw_roll` | `diag(-1,1,1)` | `(w,x,-y,-z)` | yaw + roll | pitch |
| `pitch_roll` | `diag(1,-1,1)` | `(w,-x,y,-z)` | pitch + roll | yaw |

⛔ **Reversing ONE axis alone is geometrically impossible** — `det(Q)` would have to
be `+1` and `-1` at once. So *"yaw is backwards"* can never be fixed on its own.

⚠⚠ **THREE OPTIONS WERE THEN TRIED ONE PER RESTART, AND THE THREE REPORTS CAME OUT
MUTUALLY INCONSISTENT:**

    run 1  pitch_yaw  (P,Y,R)=(1,1,0)  wrong: yaw          => yaw should be 0
    run 2  pitch_roll (1,0,1)          wrong: yaw, roll    => yaw 1, roll 0
    run 3  yaw_roll   (0,1,1)          wrong: roll, pitch  => pitch 1, roll 0

    pitch -> reverse   (consistent)
    roll  -> do NOT    (consistent, twice)
    yaw   -> runs 1 and 2 DIRECTLY CONTRADICT

✅ **A live A/B settled it in one session.** An `'m'` key was added to the debug tool
to cycle the options on ONE camera, ONE pose, no restarts. The owner cycled all four
and stopped: *"the setup I closed with is the correct one"* — **`pitch_yaw`**.

⭐⭐⭐ **THE METHOD RULE, AND IT IS THE MOST REUSABLE THING IN THIS ROW: WHEN ONE
OPTION PER RESTART PRODUCES INCONSISTENT REPORTS, THE INSTRUMENT IS THE PROBLEM,
NOT THE OBSERVER. A/B ON ONE POSE INSTEAD.** ⚠ And it matters *here* for a specific,
checkable reason: **the open YAW-LEAN defect makes the cube ROLL WHILE IT YAWS** by
up to ~27°. Two of the three axes being judged are coupled by a known bug, so a
per-axis verdict by eye was asking for something the eye could not give. Three
sessions and three contradictory reports were spent before that was noticed.

⛔⛔ **AND ONE MORE STORY IS RETRACTED.** While `yaw_roll` was briefly the default it
was written up as *"the one with the cleanest physical meaning"* — the inverse of
the `cv2.flip` mirror, since a mirror preserves nodding and reverses turning and
tilting. Sound about mirrors, wrong about this pipeline, and reached by reasoning
BACKWARDS from a live report instead of forwards from the geometry. ⚠ Kept on
purpose: a tidy physical story is exactly the kind of thing that gets believed
twice.

⭐ What survives intact: §2's hybrid diagnosis, §3's independent z-translation
finding, and §4's proof that the landmarks need not be touched.

## 7. ⚠ What is owed, and one artifact that cannot be coded away

⛔ **The owner's live look, in BOTH tools** (`METHOD.md`: automated green is
necessary, not sufficient). Until then the default stays `legacy`. Run it with
`CAMERA_MOUNT=facing_user` — no edit needed.

⚠ **The hand's video image still grows as it moves away from the user**, because
the video underneath is the camera's and cannot be flipped, while the cube now
shrinks. They change size in opposite directions. That is inherent to the
simulation the owner described — *"it is only a simulation since the hands are not
placed at the same distance and focal from the camera as from the user's eyes"* —
and it is the thing to watch for in the live look.

⭐ **Scale needed no work, which was checked rather than assumed.**
`projected_size_px = nominal × reference_depth / depth_m` and the focal cancels, so
with `depth_m` kept in metres-from-camera the cube shrinks as it recedes on its
own. Absolute hand dimensions are used in exactly two places — `NOMINAL_SPAN_M`
(absolute depth, gates snap) and the 42.5 mm half-hand-breadth play-volume margin —
and a `z` sign touches neither. The ratio estimator cancels scale by construction.

⛔ **`head_worn` is BUILT BUT UNVALIDATED.** There is no head-worn corpus and no
glasses to run it on; it is a coherent configuration derived from the same
geometry, not a measured one. ⚠ Do not report it as working until something has
actually run it.

## 2026-08-30 — review: `hand_frame` had become the FOURTH place that knows about the camera

⛔⛔ `V1`'s rule is `CONSTRAINTS` §7bis — *"do not add a fourth place that knows about
the camera"* — and `RB1`'s `hand_frame` did exactly that: it read its **own** env var,
`HAND_MOUNT`, while the shipped path reads `CAMERA_MOUNT`. Setting one left the other
on its default, so chirality and identity could resolve in one frame while orientation
resolved in another. **Each module individually consistent; the composite a hybrid** —
the precise defect that caused the `1.7.42` rebuild, reproduced inside it.

⚠ No divergence in the running build, because `hand_frame` is not wired yet. It would
have become one the moment `RB5` landed. ✅ Found by review 2026-08-30, before wiring.

⭐ **The fix: the mount is DERIVED.** `hand_frame.MOUNT = resolve_mount(camera_mount.MOUNT, HAND_MOUNT)`.
`HAND_MOUNT` survives only as an explicit harness override that must **agree**, and a
genuine disagreement **raises** — there is no configuration in which reading two
viewpoints is the right answer. ⭐ `resolve_mount` is a pure function, so the golden
vectors exercise every combination without touching the environment (`F1`'s void take
came from a switch verified where it was SET rather than where it took EFFECT).

⚠ `CAMERA_MOUNT=legacy` resolves to `facing_user` with a warning rather than raising:
it is `A10`/`parity_replay`'s diagnostic baseline and must stay runnable, and this
module has no legacy mode by design. ✅ Verified: the legacy baseline still passes.
