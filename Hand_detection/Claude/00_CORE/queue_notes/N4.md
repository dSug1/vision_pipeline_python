## Appended 2026-08-25 — ✅ FIXED IN THE RECORDERS, after it cost a real take

⛔⛔ **It finally bit.** The owner's live acceptance take for `F1`'s rule-3 removal
ran in production and **recorded nothing**:

```
[record] cannot record, continuing WITHOUT it: [WinError 21] The device is not ready
```

Production's `_record_open` tried the capture root **once**, then set
`VISION_RECORD=0` so it would not retry every frame. The session was otherwise
clean, so the only evidence for a production acceptance take was what the owner
saw on screen.

⭐⭐ **THE RETRY EXISTED THE WHOLE TIME — in the wrong place.**
`tools/wake_e_drive.py` had it, where only a human running it by hand benefits.
⚠ **And running it beforehand is not a workaround**: E: sleeps again during
whatever runs next. That is exactly what happened — the drive was woken, the
*debug* take ran and recorded fine, and by the time production started it had
slept again.

### The fix

* **`Resources/capture_drive.py`** — `ensure_awake(root)`, the retry, in one place
  (`N6`). The probe **writes** rather than checking existence: a sleeping drive can
  report a path as present and still refuse to open a file in it.
* **Both recorders call it** before their session directory is created —
  production's `_record_open` and `LiveSnapDebug`'s preflight.
* **`tools/wake_e_drive.py` now delegates** to the same function, so running it by
  hand is a convenience rather than a precondition.
* ⭐ **Production's failure message is now LOUD and repeated** — a take the
  operator believes is recording and is not is worse than a refused one, and
  production has no on-screen recording indicator.

### Verified against the real fault, not a simulation

The drive had genuinely slept again by the time the fix was tested:

```
[wake] attempt 1/8 failed: PermissionError [WinError 21] The device is not ready
[wake] drive awake and writable (attempt 2)
[record] RECORDING -> ...\2026-08-25_222105_wake_fix_selftest
```

⭐ Attempt 1 reproduced the exact error that lost the take; attempt 2 recovered.
`analysis/verify_capture_drive.py` (7 checks) pins the behaviour, since the real
fault cannot be summoned on demand — you cannot ask a USB enclosure to sleep.

⚠ **Still unaddressed**: the volume's `Full Repair Needed` / HealthStatus=Warning
flag. This handles SLEEP only.
