## Appended 2026-08-25 — sequencing fixed, Unity ruled out, feasibility checked

⭐ **SEQUENCED: the platform decision comes RIGHT AFTER `F1`** (owner). `F1` is
perception-only, so it accrues no throwaway work; everything renderer-shaped
waits.

⛔ **UNITY IS OUT, deliberately re-affirmed** (owner): *"keep as it is currently.
if ever we will move to Unity, we will do another project to port it to C#"* — so
a Unity build is a **separate project**, not a migration, and C# is not a
candidate in this decision.

⭐⭐ **Feasibility findings that change the shape of the choice** (full write-up:
`50_PORT_WEB_MOBILE/INDEX.md`):

* ⛔ **iOS standalone PWA + camera is broken/unreliable** and the permission is
  not persisted; the documented workaround is to stop being a PWA and run in a
  Safari tab. **This is the strongest argument against browser-only.**
* ⭐ **MediaPipe ships FIRST-PARTY Android / iOS / Web / Python SDKs**, so native
  Swift/Kotlin carries **no third-party binding risk**.
* ⛔ **React Native / Flutter is the risky middle** — no official or widely
  adopted live hand-tracking plugin, community ones largely Android-only, each a
  separate `N13` clearance.
* ⚠ **Mobile frame rate is unmeasured.** `L1` showed the rate is camera-bound
  here, not compute-bound — but that was a desktop webcam.

## Appended 2026-08-25 (later) — the Model Card's warning for the port

> *"The model has not been tested in 'in-the-wild' smartphone camera conditions,
> including low-end devices, low light, motion blur etc., that can affect
> performance."* and *"trained on limited datasets and is meant for experimental
> usage."*

⚠ The corpus is one operator, one desk, one webcam. **Mobile is unmeasured on
both axes** — frame rate (`L1` proved the rate is camera-bound *here*) and
landmark quality. ⭐ Cheap mitigation when the port starts: the recorders and the
whole `analysis/` suite already run on any JSONL take, so a phone take can be
